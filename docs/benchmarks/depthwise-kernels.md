# Depthwise backward and compiled normalization findings

These measurements are from RTX 5090, MedNeXt Base, input `[1,1,128,128,128]`,
three classes, BF16, deep supervision enabled, checkpointing disabled, and cuDNN
autotuning enabled. PyTorch 2.12.0+cu132, cuDNN 9.20.0, driver 595.84.
Values are per-step kernel durations from separate three-step instrumented traces.

## GroupNorm after compilation

| Mode | Attributed time | Total kernel time | Share |
|---|---:|---:|---:|
| Eager: native GroupNorm forward + backward | 17.242 ms | 100.949 ms | 17.08% |
| Compiled: kernels with `group_norm` in their names | 5.012 ms | 75.464 ms | 6.64% |
| Compiled, eight classes: same name-matching rule | 5.084 ms | 77.003 ms | 6.60% |

The compiled row includes fused casts and neighboring operations. It is not an
isolated GroupNorm cost, nor a claim that normalization alone became exactly
3.44x faster. The trace establishes that standalone eager normalization kernels
were replaced by a substantially cheaper set of fused kernels containing
normalization work. Kernel-name attribution may change between compiler versions.

## High-resolution depthwise backward

The compiled trace's backward operator group with input `[1,32,128,128,128]`
and weight `[32,1,3,3,3]` aggregates four regular high-resolution blocks:

| Work | Kernel ms per training step |
|---|---:|
| Weight gradients | 11.777 |
| Input gradients | 3.878 |
| Total | 15.655 |

The weight-gradient kernel name begins
`at::native::...::conv_depthwise3d_cuda_backward_weight_kernel`.
This identifies a PyTorch native CUDA kernel in the measured path, not a Triton
kernel generated by torch.compile. Compilation did not remove this bottleneck.

For each channel and kernel offset, weight-gradient computation reduces products
of the input and output gradient over batch and spatial positions. With 32
channels and a 3x3x3 kernel there are only 864 weight gradients, each reducing
roughly 128^3 positions at batch size one (with padding masks at boundaries).

A proposed optimization experiment, not an implemented or measured speedup:

1. Isolate this exact operator and benchmark input-gradient and weight-gradient
   work separately using the same shapes, dtypes, strides and backend versions.
2. Inspect the existing kernel and measure occupancy, memory throughput, register
   use and reduction behavior with Nsight Compute. Kernel durations alone do not
   prove a particular hardware limit.
3. Test a tiled weight-gradient reduction: split spatial positions across many
   blocks, accumulate FP32 partial sums, then reduce those partials. Reuse input
   and output-gradient tiles across kernel offsets where beneficial. Tune tile
   sizes and reduction strategy for each architecture. Scratch memory, an extra
   reduction launch, and changed summation order are explicit tradeoffs.
4. Implement as a CUDA extension or Triton operator with registered autograd.
   Initially retain the existing forward and input-gradient paths; replace only
   weight gradients where measured beneficial, with a fallback for other shapes.
5. Check forward and both gradients against PyTorch, including padding, strides,
   batch sizes, dtypes, and compiled training. Measure whole-step speed after
   integration; a microkernel speedup does not translate directly to the model.

Halving only this 11.777 ms weight-gradient contribution would save approximately
5.9 ms per profiled step: roughly an 8% step-time reduction, or 1.08x throughput,
if all other work and overhead remained unchanged. This is an estimate, not a
benchmark result. It explains why this is a focused next experiment rather than
a promised multi-fold end-to-end speedup.

The architecture, groups, channels, kernel size and mathematical gradients need
not change. Simply replacing depthwise convolution with an unrestricted dense
convolution or reducing channels/kernel size would change the model.

References: [PyTorch native depthwise 3D CUDA implementation](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/DepthwiseConv3d.cu),
[integrating Triton kernels and autograd with torch.compile](https://docs.pytorch.org/tutorials/recipes/torch_compile_user_defined_triton_kernel_tutorial.html).
The linked source tracks main; use the exact installed release when implementing.

# Split-reduction prototype results

An opt-in Triton prototype implements the proposed two-stage reduction for the
measured `[1,32,128,128,128]`, cubic odd-kernel, stride-one, same-padding weight
gradient. The module falls back to PyTorch at other input shapes.

For 3x3x3 on RTX 5090 BF16 and PyTorch 2.12, its isolated latency was 1.007 ms
versus 2.852 ms for ATen (2.83x). Four calls in the compiled Base trace totaled
3.740 ms versus 11.255 ms for the original high-resolution native dW calls. Full
three-repeat compiled medians improved from 73.661 to 64.947 ms (3 classes) and
74.871 to 66.712 ms (8 classes).

For 5x5x5, the generic split kernel measured 3.711 ms versus 14.260 ms for ATen
(3.84x). Matched full-model compiled medians improved from 228.319 to 179.224 ms
(3 classes) and 228.473 to 182.865 ms (8 classes), reductions of 21.5% and 20.0%.
The 64-split FP32 scratch buffer grows from 0.211 MiB at 3x3x3 to 0.977 MiB at
5x5x5; measured peak model allocation was effectively unchanged.

Raw profiler artifacts are intentionally excluded from the repository; use the current scripts under `benchmarks/` and `tools/` to reproduce a matched run.

The next regular resolution also benefits in isolation. At `[1,64,64,64,64]` with
64 channels and a 3x3x3 kernel, ATen dW measured 0.720 ms and the best split launch
measured 0.253 ms (2.85x), using eight splits and block size 1024. Integrating this
path with the existing 128-cubed split and pointwise GEMM reduced PyTorch 2.14
compiled medians from 68.090 to 66.116 ms (3 classes) and from 69.517 to 67.791 ms
(8 classes).

Smaller regular dW shapes still improved as isolated kernels, but with diminishing
whole-model value: 32 cubed 0.197 to 0.072 ms (2.73x), 16 cubed 0.060 to 0.029 ms
(2.05x), and 8 cubed 0.036 to 0.027 ms (1.34x). Across their actual call counts,
their combined ideal saving is only about 0.64 ms before integration overhead.

The tuned launch uses 64 spatial splits, 1024 elements per program, FP32 partials,
and a second reduction. It is not yet tuned for another architecture or resolution.

## Current all-regular dW+dX path

The implemented dispatch now includes all regular Base resolutions `(C,S)` of
`(32,128)`, `(64,64)`, `(128,32)`, `(256,16)`, and `(512,8)`, and replaces both
dW and dX. The 18 matching stride-one same-padding modules use the generic odd
kernel implementation; downsample and transpose layers remain native PyTorch.

On RTX 5090 with PyTorch 2.14, BF16, compilation, and pointwise GEMM, this changed
the three-class median from 66.116 ms for the 128/64 dW-only version to 63.815 ms;
eight classes changed from 67.791 to 65.491 ms. The corresponding original-Conv3d
medians were 96.176 and 97.615 ms. In an instrumented three-class step, custom dW
launches totalled 5.481 ms and custom dX launches totalled 3.110 ms.

dB is a channel-wise sum of grad-output. The isolated 128-cubed BF16 reduction was
0.108 ms, versus 0.980 ms for dX. It remains a native PyTorch call because a custom
or fused dB path has little expected whole-model value at this point.

## Stride-two depthwise component benchmark

`benchmark_depthwise_stride2.py` measures ATen's dX, dW, dB, and combined
backward calls without a custom kernel. On RTX 5090/PyTorch 2.14/BF16, the largest
ordinary downsample (`C=32`, input `128^3`, output `64^3`) took 1.665 ms combined:
dX 1.255 ms, dW 0.412 ms, and dB 0.022 ms. It is dX-dominated, so a dW split
reduction alone cannot yield a material end-to-end improvement.

The largest transpose-depthwise layer (`C=64`, input `64^3`, output `127^3`) took
3.669 ms combined: dX 0.459 ms, dW 3.085 ms, and dB 0.196 ms. dW is 84% of this
backward call, making transpose-depthwise dW the next depthwise custom-kernel
candidate. Its indexing differs from regular Conv3d, but it still has the same
parallel partial-reduction structure: reduce input/grad-output products over
spatial positions into FP32 partial weight gradients, then finish the reduction.

The transpose dW implementation is now integrated for the C64, input-64³ Base
block. Its isolated BF16 timing is 0.409 ms versus 3.052 ms for ATen. Three
isolated compiled training repeats with pointwise GEMM and all regular dW+dX paths
gave medians of 59.765 ms (3 classes) and 62.698 ms (8 classes), compared with
96.176 and 97.615 ms for the original Conv3d configuration. Native transpose dX
and dB remain in place.

In these historical experiments, stride-two downsample dX was opt-in through
the benchmark's `--depthwise-stride2-dx` flag. Its isolated C32,
input-128³ BF16 timing is 0.578 ms versus 1.253 ms for ATen. In the full compiled
model, however, enabling it raised the 3-class median from about 59.1 to 60.4 ms,
because splitting native dW/dB from custom dX introduces graph and scheduling
overhead. That historical experiment retained native downsample dX. Current
policy v2 includes a shared downsample-dX rule based on subsequent cross-device
operator evidence; this earlier model-level counterexample remains relevant
when evaluating the combined policy. No new whole-model improvement is implied.

## Per-shape automatic selection

`mednext-accel profile` discovers the shapes created by the chosen MedNeXt
variant, finds a maximum feasible batch, and benchmarks eligible pointwise and
depthwise implementations there. It writes immutable evidence JSON and a
separate runtime policy YAML. The complete provisional policy is compared
against the reference model before positive rules are published. Parameter
objects and state-dict keys remain unchanged. See the current
[optimization guide](../optimization.md) for shared and per-SM inference,
negative overrides, and output semantics.

## Batch-aware RTX 5090 tuning

The historical batch-aware policy kept the batch-one launches above and selected measured
dW splits for batches 2, 4, and 6. Pointwise convolution backward showed a
separate cuDNN algorithm cliff once the batch dimension exceeded one. For the
measured Base shapes, independent per-sample GEMMs avoid that cliff while
preserving parameter objects and state-dict paths.

The table below uses MedNeXt Base, 128 cubed input, BF16, three classes, deep
supervision, AdamW, `torch.compile(mode="default", fullgraph=True)`, all-expansion
checkpointing, five warmups, and 20 measured steps. Each row is one run.

| Batch | Previous policy | Batch-aware policy | Reduction | Samples/s | Peak allocated |
|---:|---:|---:|---:|---:|---:|
| 1 | 64.19 ms | 64.02 ms | 0.3% | 15.62 | 3,762 MiB |
| 2 | 161.17 ms | 149.11 ms | 7.5% | 13.41 | 8,459 MiB |
| 4 | 326.58 ms | 306.12 ms | 6.3% | 13.07 | 16,729 MiB |
| 6 | 501.32 ms | 465.77 ms | 7.1% | 12.88 | 21,992 MiB |

Without checkpointing, batch two improved from 151.58 to 134.06 ms, an 11.6%
step-time reduction. Its throughput increased from 13.19 to 14.92 samples/s.
The batch-six peak-allocation reduction was reproduced in two independent runs;
it comes from avoiding the native pointwise algorithms and their larger
temporary storage. These selections remain specific to the measured GPU and
software stack. Current policy v2 uses bounded pointwise interpolation and
structurally scaled depthwise launches; unmeasured batches can receive optimized
choices. See [SM120 policy evidence](sm120-profile.md) for the current bounds.
